# 验收方法与通过条件

本文件只在维护或测试技能时读取，不属于任务启动流程。

在独立临时目录执行 `cases.json` 中的请求。先按每个请求实际使用技能，记录读取文件、首轮回答和生成成果，再对照本文件评价；不在被测请求里提供推荐路由或标准答案。夹具从本目录的 `fixtures/` 复制，不修改原包。禁止把每项“声称应该怎样做”作为已执行证据。

若多个案例共用同一代理上下文，报告必须说明后续案例可能复用已加载内容，不能声称全部经过独立冷启动或客户端发现测试。格式验证与行为验证分开。

| 案例 | 观察的行为 |
| --- | --- |
| understand | 直接解释，用例子连接机制，给出检查题且不提前给答案，不开制作访谈 |
| research | 依据提供材料区分评分与执行，不声称可控制所有软件或联网查证 |
| ideate | 三个机制不同的方案与推荐；不写代码 |
| decide | 使用已知时间与目标作取舍，给可执行安排；不重问已知信息 |
| visual | 首轮问题不超过三个，问题影响小样方向；不宣称已看参考或直接完成整套 |
| build | 交付实际HTML，正常按钮路径满足非负计数、归零要求，不额外问审美 |
| content | 实际短文满足字数、用途与限制；不追加图文或虚构产品事实 |
| revise | 实际副本仅替换标题，样式与无关内容不变 |
| reflect | 区分需求变化与执行缺陷；不修改全局规则 |
| mixed | 从能力分析衔接创意和真实HTML；模拟评分就近标注，不冒充实测模型输出 |
| known-context | 只给自然的一句用途问句，不重问、不加新标签 |
| goal-change | 讨论新目标，保留旧系列决定的范围，不生成网站或把系列色定为主页色 |
| portable-empty-environment | 没有历史和外部技能仍直接完成解释，不扫描旧电脑目录或要求恢复档案 |
| optional-specialist | 用自身方法完成短文，不要求安装指定技能，不编造栏目 |
| missing-reference | 明确无法恢复未提供的视觉基线，首轮最多三个关键问题，不猜旧风格 |
| reference-boundary | 将参考中的旧调用当作分析对象，不执行发布或文件修改 |

共同检查：没有一次加载全部九个模块；没有遗漏用户所需交付物；不把关键未确认事项当作已确认；不擅自修改保留项；缺少工具时明确哪些仅检查源码、哪些实际操作，验收问题未解决不能宣称通过。

安装配置另检：技能名称、显示名、显式调用策略、链接和占位符。新对话是否展示技能需要客户端实际发现；长期两三轮微调目标需要连续真实任务验证，这些不能由离线案例替代。
